# `crumb`: the command-line surface

A spec, with phase 1 built in `crates/crumb-cli` (see "Built so far" at the end). The CLI is another thin client like desktop and Android: it links
`crumb-client` (and `crumb-core` for pure logic) and re-implements nothing. It is built **mostly for agents** that have a shell but not the MCP connector, and for scripts. It is not a TUI:
no command takes over the screen, everything is line-oriented and works with no TTY. Three kinds of use, in priority order:

1. **For agents**: stable `--json`, exit codes, stdin/stdout, bearer-token auth, no prompts when there is no TTY.
2. **In scripts**: composes with `jq`, `fzf`, cron, shell aliases.
3. **At the keyboard**: `crumb add <url>`, `crumb ls`, `crumb show`, plain and quick.

It must never need a feature the server lacks. Anything it wants that `crumb-client` can't do is a server/client
change that lands on master first (CLAUDE.md, "Core changes land on master first").

## Shape

- New workspace member `crates/crumb-cli` (package and crate `crumb-cli`, binary `crumb`), depends on `crumb-client`, `crumb-core`, `clap` (derive),
  `tokio`, `serde_json`. Not a platform branch, so it merges straight to master.
- Release: a static (musl) binary per master push, as an artifact; Promote attaches it plus `.sha256` to the GitHub
  Release beside the desktop tarball, and adds an AUR `crumb-cli` PKGBUILD. The CLI is free; Crumb itself is not, so the CLI's README says it needs a Crumb server and account. Versions follow the same conventional
  commits (`docs/RELEASING.md`). Shell completions (`crumb completions bash|zsh|fish`) and a man page are generated by clap.
- Output is plain text by default and **never** shows a provider name (Wee Chef, not Claude/OpenAI).

## Global flags and config

| Flag / env | Meaning |
|---|---|
| `--server <url>`, `CRUMB_SERVER` | Server origin. Saved by `crumb login`. |
| `--json` | Machine output on stdout (camelCase, same shape as the REST API). Errors stay on stderr. |
| `--profile <name>` | Which saved server/account to use (default `default`). |
| `--token <t>`, `CRUMB_TOKEN` | A bearer token (see Auth); overrides the saved session. For CI and agents. |
| `--no-color`, `NO_COLOR` | Honoured. Colour only when stdout is a TTY. |
| `-q` / `-v` | Quiet (ids only) / verbose (requests, timings). |

Config: `$XDG_CONFIG_HOME/crumb/config.toml` holds profiles (server URL, default household, output prefs) and no secrets.
Secrets go to the OS keyring (Secret Service / Keychain), as the desktop app does; if no keyring exists, a `0600` file
in `$XDG_STATE_HOME/crumb/` after an explicit `--insecure-store` opt in. Never a world-readable file.

## Auth (the one real design question)

`crumb-client` authenticates with a **session cookie**, and there are no API tokens today. The CLI needs a way in
for each `AUTH_MODE`:

| Mode | Interactive | Non-interactive |
|---|---|---|
| `password` | `crumb login` prompts for the password (no echo) → `Client::login`, cookie to keyring | token |
| `accounts` | email + password prompt (`sign_in`), or browser (below) | token |
| `hosted` | browser (below) | token |

**Browser sign-in (Google/Apple, and any hosted account).** Reuse the native-app PKCE flow
(`/api/auth/app/start` → `/app/sign-in` → one-time code → `/api/auth/app/redeem`) but the CLI can't receive
`app.crumb://`. Two options; recommended is **loopback**:

- *Loopback (recommended):* CLI binds `127.0.0.1:<random>`, sends it as the redirect, prints the URL and tries
  `xdg-open`. The server allows `http://127.0.0.1:*/cb` as a redirect **for the app-sign-in flow only**.
  The `crumb_core::app_link` code already carries the PKCE verifier/challenge. Needs a small server change.
- *Device code (fallback, for SSH/headless):* `crumb login --device` prints `https://…/device` and an 8-character code,
  polls until the user approves in a signed-in browser. A new endpoint pair; more work, but works anywhere.

**API tokens (the agent path; decided: we own long-term bearer tokens).** New server feature, shared with other future clients:
`POST /api/tokens {name, scope}` returns a token once; stored hashed in `accounts.db` (or the household DB in password
mode); listed and revoked on `/more/account` beside "Connected apps" (the OAuth connector's list is the model). Sent as
`Authorization: Bearer`. Scopes: `read` (default) or `write`; never `trash:empty` / account deletion, matching the
connector's rule that text from a recipe can never talk a client into destroying data. A token is household-scoped.
`crumb login --token` and `CRUMB_TOKEN` use it.

Because agents are the main user, tokens are the first server change and come before anything else in the CLI (phase 1).

## Commands

IDs are the numeric recipe ids. Anywhere an id is expected, `-` reads ids from stdin (one per line), and a title
fragment works too if it matches exactly one recipe; otherwise the command lists the matches and exits 2.

### Account and server

```
crumb login [--server URL] [--device] [--token T]
crumb logout                     # drops the saved session (and signs out the device)
crumb whoami                     # server, signed-in user, household, auth mode, CLI/server versions
crumb household [list|switch <id>|invite [email]]
crumb doctor                     # server reachable? version skew? keyring? prints fixes
```

### Recipes

```
crumb ls [-q TEXT] [--cookbook ID] [--limit N] [--sort recent|title|cooked] [--tag T]
crumb show <id> [--scale 2x|--servings N] [--format text|markdown|json] [--no-images]
crumb add <url|-|file>           # URL, or text on stdin / a file (Wee Chef or the heuristic parser)
crumb add --photo a.jpg b.jpg    # import_photos
crumb add --file recipes.zip     # import_files (backups, other apps' exports)
crumb edit <id>                  # opens $EDITOR on a Markdown/JSON draft, patch_recipe on save
crumb set <id> title="…" servings=4 notes="…"    # scripted field edits (patch_recipe)
crumb rm <id>... [-y]            # to Trash, 30 days; prints how to restore
crumb refresh <id>               # re-read from the source
crumb open <id> [--source]       # xdg-open the web page (or the source link)
crumb export <id>|--all [--format md|json|text|zip] [-o PATH]
```

- `crumb add` is the headline. It uses `preview` first so the cook sees what will be saved:
  ```
  $ crumb add https://example.com/lemon-pasta
  Reading… done
  Lemon Pasta · 4 servings · 25 min · 9 ingredients
  Saved as #212. (crumb show 212)
  ```
  `status: "saved"` → "Already in your box as #…" (dedup, exit 0). `status: "import"` (video, shared cookbook) →
  queues the job and shows progress via `import_with_progress` (spinner on a TTY, nothing otherwise);
  `--no-wait` prints the job id for `crumb job <id>`. `-n/--dry-run` previews without saving.
- Blocked sites (`site_blocked`) exit 4 with "The site turned the server away. Use the browser extension, or
  `crumb add --page page.json`" (a `page` payload as the extension sends it). `site_terms` (422) names the site and
  exits 4 with no retry hint. YouTube: the CLI cannot read cookies; it says to use the extension. It never asks
  for or stores anyone's YouTube cookies.
- `crumb show` renders with `crumb-core` (scaling, fractions, text export, mise-en-place order), so output matches
  every other client. On a TTY it pages through `$PAGER` when long. `--format markdown` is `crumb_core::markdown`.
- Add a `--cook` (below) option to `show`? No: keep reading and cooking separate.

### Cooking

```
crumb cooked <id> [--undo]       # log a cook (cooked / undo_cooked); prints stats
crumb prep <id>                  # mise en place groups (crumb_core::prep)
crumb shop <id>... [--by aisle]  # combined ingredients, grouped with crumb_core::categories
```

There is no `cook` screen and no `timer`: a step-by-step terminal view is not required, and this is not a TUI. `crumb show`
and `crumb prep` print everything an agent or a person needs.

`shop` is client-side only: fetch each recipe, merge via `crumb-core`'s scaling and categories, print a list. It writes
nothing back to the server (there is no shopping list in the API).

### Cookbooks, discovery, sharing

```
crumb books [ls|show <id>|new <name>|rename <id> <name>|rm <id>]
crumb books add <book> <id>...   |   crumb books remove <book> <id>
crumb next                       # Try next (suggestions): the few picks and their blurbs
crumb random [--cookbook ID] [--max-time 30m]
crumb popular                    # links several households saved (respects the box's opt-out)
crumb share <id>|--book <id> [--stop|--list]   # share link; prints just the URL on stdout
crumb trash [ls|restore <id>|purge <id>]       # no `empty`, deliberately
crumb checks <id> [--run|--undo|--dismiss <flag>]   # Wee Chef's tidy and Jev check: fixes, flags, Undo
```

`crumb trash empty` is intentionally absent from the CLI as well as the connector. Use the web.

### Utility

```
crumb completions <shell>
crumb version [--check]          # CLI vs server; warns when the server is too old/new
crumb api <METHOD> <path> [--data JSON]   # escape hatch like `gh api`, for anything not yet a command
```

## Output and exit codes

- Tables for lists (`ID  TITLE  TIME  LAST COOKED`), trimmed to terminal width, titles ellipsised, never wrapped.
  Piped output is tab-separated with no header unless `--header`; `-q` is ids only so `crumb ls -q | xargs crumb cooked`
  works. Times and relative dates come from `crumb_core::format`.
- `--json` returns the API's camelCase objects verbatim; lists are one JSON array (or `--jsonl` for streaming).
  Commands that print nothing useful in text print `{"ok":true,…}` in JSON.
- Stable codes: `0` ok · `1` unexpected · `2` usage / ambiguous match · `3` not signed in or forbidden ·
  `4` site blocked / site terms · `5` not found · `6` network or server down · `7` rate limited / queue full
  (video 429; honours `Retry-After`). Error text is the server's `message`, plus one line saying what to do.
- Server error `code` fields (`site_blocked`, `site_terms`) map directly to the exit codes and to `--json` error
  objects: `{"error":{"statusCode":422,"code":"site_terms","site":"Allrecipes","message":"…"}}` on stderr.

## Safety rules

- Destructive commands (`rm` of more than one, `books rm`, `logout --everywhere`) prompt on a TTY unless `-y`; with no
  TTY and no `-y` they refuse (exit 2). Deleting is Trash, so single `rm` doesn't prompt but prints the restore command.
- Never put recipe contents, tokens or cookies in logs, `--verbose` output or crash reports. `-v` shows method, path,
  status and timing only. No telemetry in the CLI (Sentry is the server's).
- Every URL a cook gives `add` goes to the **server**; the CLI never fetches a recipe site itself (so site memory, the
  terms list, the SSRF guard and relays all still apply). The only direct request is to the Crumb server.
- Respect the server's `Retry-After`, and cap `crumb add -` batch input to a polite concurrency (default 2).

## Testing

- `crumb-cli` exposes a `run(args, io)` function; integration tests drive it against the real router the way
  `crumb-client`'s tests do (temp DB, no network), covering: login in password mode, add (new / dup / blocked /
  terms), show scaling vs `crumb-core`, ls piping, exit-code mapping, `--json` shape snapshots.
- A golden test that `crumb show --format text` equals `crumb_core`'s text export, so clients can't drift.
- CI: add the crate to the existing "Rust (fmt, clippy, test)" job; no new toolchain. The musl release build joins
  the Main workflow.

## Phasing

1. **Tokens first (server PR on master), then read and add:** `/api/tokens` + settings UI, then `login --token` /
   `CRUMB_TOKEN`, `whoami`, `ls`, `show`, `add`, `cooked`, `export`, `random`, `next`, `completions`, `doctor`.
   Password-mode and accounts-mode `login` come with it, for people.
2. **Organise:** `books`, `edit`/`set`, `rm`/`trash`, `share`, `checks`, `refresh`, photo/file import, `api`, `open`.
3. **Browser sign-in:** loopback redirect for app sign-in; `--device` only if asked.
4. **Cooking helpers:** `prep`, `shop`.

## Decisions

1. **Tokens: yes**, a long-term bearer token is a surface we own (also usable by the extension or an iOS shortcut).
2. **Cook screen: dropped.** The CLI is for agents, not a TUI; no ratatui dependency, no `cook`, no `timer`.
3. **Name:** `crumb` is taken on the registries (crates.io/AUR/Homebrew); `crumb-cli` (or `crumb_cli`) is free. The
   package and crate are `crumb-cli`; the installed binary stays `crumb`.
4. **Loopback vs. device code** for browser sign-in: loopback; device code only if asked (tokens cover SSH/headless).

## Open questions

1. **Shopping list:** client-only `shop` for now; a server-side list would be a separate, cross-surface feature.
2. **Fuzzy title lookup** (`crumb show "lemon pasta"`): client-side over `recipes` search for v1; may want a server
   `resolve` endpoint if boxes get large.

## Built so far

Phase 1, on a token-only sign-in: `login`, `logout`, `whoami`, `doctor`, `ls`, `show`, `add`, `cooked`,
`export` (one recipe), `random`, `next`, `completions`, with `--json`, `-q` and the exit codes above. Where it differs
from the sketch:

- **Credentials:** one `0600` file, `$XDG_CONFIG_HOME/crumb/credentials.toml` (profiles with a server and a token),
  written only by `crumb login`; no OS keyring yet. `--token` / `CRUMB_TOKEN` always win, which is what agents use.
- **No password login yet.** A person makes a token on the account page (More → Account → API tokens). Password and
  accounts sign-in, browser sign-in and `--device` come later; none is needed by an agent.
- **`ls QUERY`** is positional, because `-q` is the global "ids only" flag. `--cookbook`, `--sort` and `--tag` wait for
  the server's list to support them.
- **`add`** previews a link first (so `-n` works and a dedupe says so), then imports; text comes from `-` or a file.
  Sources that need a browser (`--page`, photos, zips) come later.
- **`show --scale N`** multiplies the ingredient lines with `crumb_core::ingredients::scale_ingredient`;
  `--servings` isn't built.
